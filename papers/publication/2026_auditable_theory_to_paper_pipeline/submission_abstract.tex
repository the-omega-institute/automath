\begin{abstract}
AI-assisted formal mathematics is often described as a loop in which a
language model proposes Lean code and a proof assistant accepts or rejects it.
That loop is useful, but it is too small to describe sustained research.  In a
live project, the hard question is not only whether a file compiles.  It is
whether a generated object is a proposal, a source-theory claim, a checked
formal interface, a finite artifact witness, a publication claim, or a human
decision boundary.

We report an auditable theory-to-paper method developed across two related
workspaces, \emph{newmath} and \emph{automath}.  The method treats
AI-assisted formalization as a typed compilation problem: generated material is
not allowed to become load-bearing evidence until it is routed through six
records--source object, formal interface, finite evidence row, advisory agent
action, deterministic gate, and human promotion boundary.  The model proposes,
repairs, and reviews; deterministic gates classify; humans promote claims into
reader-facing research output.

The contribution is a portable audit boundary for formal-mathematics
automation, not a new theorem prover or an automatic venue-acceptance system.
The accompanying supplement proves a conditional finite-record interface
theorem for the submitted support rows.  It does not assert proof-assistant
correctness, full source-tree semantic completeness, dynamic artifact
soundness, implementation soundness of every gate, public-byte equality, or
venue acceptance unless those stronger readings are supplied as separate
accepted records.
\end{abstract}

\section{The ceiling outside the proof assistant}
Proof assistants are excellent at checking the obligations they are given.
They do not, by themselves, decide whether an AI-generated theorem statement is
mathematically substantive, whether it duplicates a submitted sibling, whether
an artifact row is being overread, or whether a draft has crossed the boundary
from intake note to active manuscript.  These failures are common in
AI-assisted formalization because models can produce coherent local objects
without preserving the global status of the research claim.

Our answer is to make claim status explicit.  A generated increment is compiled
into records before it is treated as progress.  Each accepted increment must
name: (1) the source object being changed, (2) the formal interface on which it
is checked, (3) the finite evidence row supporting the claim, (4) the advisory
agent action that proposed or repaired it, (5) the deterministic gate that
accepted it, and (6) the human promotion boundary that says what may be claimed
to readers.  If one of these roles is missing, the increment remains a
proposal, not evidence.

\section{Two instances}
\emph{Newmath} is the structured-source instance.  Its BEDC workspace separates
theory source, Lean-facing interfaces, and finite substrate witnesses.  Lean
markers record one verification axis, but Lean acceptance is not treated as
BEDC semantic closure.  Source paths, proof obligations, compiler contracts,
and limitation rows remain separate evidence coordinates.

\emph{Automath} is the research-publication instance.  It coordinates
theoremization, formalization, review, and manuscript assembly through source
maps, theorem inventories, overlap/submitted gates, novelty checks, stage
reviews, and submission packets.  Its purpose is not merely to write papers.  It
records which generated objects are source claims, which are checked
interfaces, which are artifact witnesses, which are still proposals, and which
are blocked by overlap, novelty, venue, or human-promotion constraints.

\section{Relation to formalization tools}
The method is complementary to proof-assistant and LLM-proving infrastructure
such as Lean~\cite{deMouraKADR2015Lean}, LeanDojo~\cite{YangEtAl2023LeanDojo},
draft--sketch--prove workflows~\cite{JiangEtAl2023DraftSketchProve}, and
formal-library artifact practice such as AFP mining~\cite{BlanchetteHMN2015AFP}.
Those systems improve the production and checking of formal objects.  The
interface here addresses a different layer: how a research pipeline decides
what kind of claim a generated object is allowed to become.

The public source surface for the BEDC instance is the newmath repository
\cite{bedc-newmath-source}, pinned for this submission to commit
\path{3fb3d6a0641767388a401883062aa522ea0b397b}.  The submitted support surface
may include the local technical supplement, source-interface record, theorem
inventory, digest manifest, and review bundle.  These files are audit support
for finite-record predicates, not a claim of fresh clean-machine rebuild,
complete source import, dynamic rerun of every artifact, or venue acceptance.

\section{Conclusion}
The useful abstraction is not ``the model proves the theorem.''  It is
``the system routes each generated object to the strongest claim it is entitled
to support.''  An auditable theory compiler makes that routing explicit.  It
lets AI agents search, repair, and criticize while keeping certification in
typed records, deterministic gates, and human promotion decisions.  The result
is a practical method for scaling AI-assisted formalization without letting
polished local output masquerade as accepted mathematical or publication
evidence.
