\begin{abstract}
AI-assisted formal mathematics needs an audit interface between generated
objects, proof-assistant checks, finite evidence rows, advisory agents, and
human publication decisions.  We present a compact publication-coordinate design
pattern for that interface.  A generated item is not promoted directly from
``model output'' to ``publication claim''; it is first assigned to one of six
roles and then to the strongest coordinate justified by finite records.  The
presentation-only contribution is the interface and its bounded checker
contract, illustrated on a theory-to-paper pipeline case from the
\emph{newmath}/\emph{automath} workspaces.
\keywords{formal mathematics \and AI-assisted formalization \and publication
audit \and proof assistants \and research automation}
\end{abstract}

\section{Motivation}

Modern proof assistants such as Lean check precise formal obligations
\cite{deMouraKADR2015Lean}, and recent AI systems help propose proof scripts or
formalization sketches \cite{YangEtAl2023LeanDojo,HorowitzEtAl2026Herald}.
For a research pipeline, however, the hard boundary is often not a single proof
obligation.  The system also has to record whether an object is a source theory,
a checked interface, a finite artifact witness, an advisory search result, a
publication claim, or a human decision.

This paper describes a design pattern for that boundary.  The aim is modest:
make the promotion rule explicit enough that an automated pipeline can search,
repair, and criticize drafts while the publication claim remains tied to finite
records and human approval.  The pattern is adjacent to proof-carrying code
\cite{Necula1997PCC} and artifact-review practice
\cite{ACM2020ArtifactBadging,ChirigatiRampinShashaFreire2016ReproZip}, but the
checked object is a publication-coordinate interface rather than an executable
program artifact.
Here the six roles name the input surfaces to separate, while the six
coordinates below are the only promoted evidence state exposed to publication
reviewers.

\section{Six publication coordinates}

The interface assigns each candidate increment to six coordinates:
\[
(\qlex,\qrgs,\qsrc,\qart,\qext,\qven).
\]
Informally, these record a lexical/source witness, a bounded record-gate
success, source-object adequacy, artifact semantic adequacy, external archive
adequacy, and venue/submission adequacy.  Each coordinate is false by default.
It becomes true only when a named finite row supplies the required evidence.
For example, a byte-indexed scanner row can support \(\qlex\), while a bounded
Horn replay over declared rows can support \(\qrgs\).  The same rows do not
automatically certify \(\qsrc\), \(\qart\), \(\qext\), or \(\qven\).

The worked case is an auditable theory-to-paper route whose public source
surface is the \emph{newmath} repository at commit
\path{3fb3d6a0641767388a401883062aa522ea0b397b}
\cite{bedc-newmath-source}.  The longer technical note and supplement contain
the row schema, manifest, digest table, replay report, and review-bundle
records.  This two-page presentation note deliberately makes only the bounded
interface claim: it describes how the finite rows determine which coordinates
may be cited, not that every imported source object is semantically correct or
freshly rebuilt on a clean machine.

\section{Checker contract and boundary}

The checker contract has three parts.  First, every load-bearing pointer is
typed: source paths, digest rows, manifest rows, review rows, and promotion rows
are separate surfaces.  Second, the transition relation is finite: row atoms are
compiled into a fixed Horn table, and forward chaining returns a coordinate
vector.  Third, nonconsequences are explicit: a successful local replay may
establish a bounded record-gate coordinate without establishing artifact
semantics, external archival status, or venue acceptance.

This separation is useful for AI-assisted pipelines because it permits agents to
be useful without making their suggestions authoritative.  A model can propose
a repair, a referee-style reviewer can reject it, and a deterministic gate can
record which finite evidence rows changed.  Human promotion then acts on a
visible coordinate vector rather than on an untyped narrative of ``the pipeline
passed''.

\section{CICM presentation}

For the CICM presentation-only route, the intended discussion is the audit
interface itself and the source-package boundary.  The non-PDF supplement may be
used to inspect the longer note, manifests, and checker records, but the PDF
claim remains the compact one above.  The presentation therefore asks a
software-and-formal-methods question: how should generated mathematical
artifacts expose the finite evidence that entitles them to become publication
claims?
