\begin{abstract}
Formal mathematics projects increasingly use AI agents for drafting,
review, theorem search, and manuscript preparation.  Ungated agent output,
however, can create theorem-looking but content-poor edits, stale source
references, duplicated submission routes, and premature paper promotion.  We
report an auditable theory-to-paper pipeline used around a Lean-backed
BEDC source workspace and an automath publication workspace.  The
pipeline separates source development, intake packets, active paper
directories, AI review loops, deterministic gates, and human promotion
decisions.  Its central rule is that AI output is advisory: load-bearing
mathematical and submission claims must be tied, at the appropriate evidence
level, to source paths, command logs, deterministic checks, and human-approved
promotion.  The safety theorem is conditional: it proves finite certificate
checkability from gate-sound acceptance entries and explicitly submitted review
surfaces, not external gate soundness, proof-assistant correctness, artifact
semantic validity, current execution of every gate, or venue acceptance.  Four
case studies illustrate the gates at the path-verified historical-snapshot
level: intake isolation, overlap/submitted blocking, fake-extension rejection,
and artifact-limitation disclosure.
\end{abstract}

\section{Problem and contribution}

AI assistance is useful in a formal-mathematics project only if the project can
distinguish proposal from evidence.  A generated theorem statement, a legal
piece of code, a mechanical expansion, or a lower score in a review rubric does
not by itself constitute mathematical discovery.  The practical publication
failure modes are equally structural: a route may overlap a submitted sibling,
an artifact status file may drift from generated counts, or an intake note may
accidentally become a daemon-visible manuscript.

This source is the long technical supplement for a presentation-only route whose
primary artifact is the two-page source \path{submission_abstract.tex}.  It
records a compact workflow pattern for avoiding these failures: an auditable
theory-to-paper pipeline in which AI agents propose, review, and triage, while
deterministic gates decide what may be treated as load-bearing evidence.  The
pattern is instantiated in local BEDC and automath workspaces.
The mathematical content of the note is the explicit safety interface for this
workflow: definitions for gate vocabulary, a pinned imported theorem spine, a
proved conditional publication-safety theorem, an evidence-level overclaim
obstruction theorem, and witness records for the four required cases.  The CICM presentation-only submission uses the short artifact plus
bibliography; this supplement and \path{review_bundle/} are evidence-support
materials rather than competing primary submissions.

The setting is adjacent to proof-assistant systems such as Lean
\cite{deMouraKADR2015Lean}, machine-learning interfaces to formal proving such
as LeanDojo \cite{YangEtAl2023LeanDojo}, informal-to-formal guidance methods
such as Draft--Sketch--Prove \cite{JiangEtAl2023DraftSketchProve}, and
large-scale formal-proof archives such as the Archive of Formal Proofs
\cite{BlanchetteHMN2015AFP}.  Our focus is different: we study the
publication-facing evidence discipline around such sources.

workspace contains Lean files, scripts, and artifact sources.  The automath
publication workspace contains intake packets, active paper tracks, review

becomes an active paper only after a human promotion decision creates a

\section{Operational interface}

For this long technical supplement and its two-page CICM presentation artifact,
the following finite interface is sufficient.

\begin{definition}[Operational acceptance interface]
\label{def:operational-acceptance-interface}
A \emph{claim} is a manuscript assertion that can affect a mathematical,
artifact, route, or submission decision.  A \emph{load-bearing claim} is a claim
whose removal would change a theorem statement, a case-study conclusion, or the
submission-readiness status.  An \emph{advisory output} is any AI-agent draft,
score, suggested theorem, review packet, or repair proposal before a gate records
it.  A \emph{deterministic gate} is a repeatable predicate, script, or checklist
whose inputs and pass/fail decision are recorded independently of the prose
generated by an agent.  A \emph{human promotion} is the explicit editorial act
that moves a candidate into publication state, for example by creating an active
\texttt{2026\_*} paper directory with \texttt{main.tex} and \texttt{PIPELINE.md}.
An \emph{evidence surface} is the set of source paths, commits, commands, logs,
inventories, and witness records cited for a claim.  An \emph{acceptance entry}
is a manuscript or submission-ledger record that marks a candidate claim as
usable in the publication-facing argument.  \emph{Accepted work} is the subset of
candidate claims with such an entry.  This is a status notion only: the
definition records that an editorial acceptance entry exists, but it does not by
itself assert external editorial acceptance or that the entry is gate-sound.  A
pipeline is \emph{gate-sound for acceptance} when each acceptance entry records
the claim kind, the evidence surface, the evidence level, and a pass record for
every gate in $\Gamma$ assigned to that claim kind, and when a route-boundary
entry also records human promotion.

The deterministic dispatch function $\Gamma$ from claim kinds to gates is part
of the operational interface.  Its domain is
\[
\{\text{formal-source},\text{ traceability},\text{ route},
\text{ submission},\text{ artifact},\text{ discovery},\text{ work-selection}\}.
\]
It sends formal-source claims to the build and axiom-purity gates; traceability
claims to inventory and marker-existence gates; route claims to promotion,
overlap, and submission-state gates; submission claims to submission-pack gates;
artifact claims to status and limitation-ledger gates; discovery claims to the
pinned discovery gate above and, for extension claims, to the theorem-content
delta gate; and work-selection claims to the scheduler gate, whose evidence
surface is a critical-path score or backlog window together with the claim kind
that the selected item is meant to advance.  For mixed claims, $\Gamma$ returns
the union of the gate sets for the claim kinds present.

The route gates have separate operational meanings.  The \emph{promotion gate}
uses the active-paper evidence surface, namely a human promotion act producing a
\path{2026_*} directory with \path{main.tex} and \path{PIPELINE.md}; passing
means the candidate may be daemon-visible publication work, and failing means it
remains intake or source material.  The \emph{overlap gate} uses route identity,
semantic-overlap ledgers, submitted-sibling paths, and program-board state;
passing means advancement is route-disjoint or has a recorded resolution, and
failing means advancement is blocked until closure, merge, supersession, or
waiting for prior feedback.  The \emph{submission-state gate} uses submission
markers, venue state, board state, and submission-pack metadata; passing means
the route's publication state permits the proposed action, and failing means the
action would duplicate, race, or under-specify an active or submitted route.  The
\emph{theorem-content delta gate} uses theorem inventories, hard-lint output, and
delta records such as \path{ARTIFACT_INVENTORY.md}; passing means that an
extension claim identifies load-bearing mathematical content, and failing means
that compilation, file churn, or surface edits may not be reported as substantive
theorem growth.

A \emph{reviewable artifact} for this paper is either a public repository file,
a supplemental file included with the submission, or an explicit
historical-evidence boundary stating that the local path is used only as
path-verified evidence and not as a fresh command-run claim.  A \emph{case
witness record} is path-complete when its evidence surface gives a
concrete source or artifact path for each load-bearing component of the row.  A
route-overlap witness has the fields \emph{route identity}, \emph{submitted
sibling}, \emph{overlap reason}, \emph{gate decision}, and \emph{allowed next
actions}.  An artifact-limitation witness has the fields \emph{artifact status
path}, \emph{limitation ledger path}, \emph{observed limitation}, \emph{gate
decision}, and \emph{allowed manuscript claim}.  A promotion witness has the
fields \emph{candidate surface}, \emph{human promotion evidence},
\emph{active-paper markers}, \emph{gate decision}, and \emph{allowed manuscript
claim}.  A theorem-content witness has the fields \emph{changed surface},
\emph{theorem inventory or hard-lint surface}, \emph{substantive-content delta},
\emph{gate decision}, and \emph{allowed manuscript claim}.  The inventory files
\path{ARTIFACT_INVENTORY.md}, \path{SOURCE_MAP.md}, and
\path{review_bundle/REVIEW_BUNDLE_MANIFEST.json} are part of the evidence surface
for this paper and give the compact path catalogue used by
Table~\ref{tab:case-witnesses}.

We distinguish two evidence levels.  A claim is \emph{path-verified} when this
paper records the relevant source path, artifact path, pinned commit or local
publication path, and gate decision, but does not assert that a command was
freshly rerun for this submission.  A claim is \emph{command-run} when the paper
also records the command, source commit, environment, exit code, and log path
for a fresh run.  This long technical supplement uses path-verified architecture
and case evidence unless explicitly marked command-run.

A uniform \emph{pass record} is the finite tuple
\[
\rho=(g,I,d,e,\ell),
\]
where $g$ is the gate name, $I$ is the input surface submitted to that gate,
$d$ is the recorded decision, $e$ is the evidence pointer supporting the
decision, and $\ell$ is the evidence level.  A pass record is assigned to a
claim certificate only when its evidence pointer is contained in the claim's
evidence surface, in a submitted manifest or table row, in a bundled snapshot, or
in an explicit historical-evidence boundary.

A \emph{publication certificate} for a load-bearing claim $c$ is the finite
record
\[
\mathcal C(c)=(K,\ell,E,H,R,D,B).
\]
Here $K$ is the nonempty finite set of claim kinds carried by $c$, $\ell$ is the
evidence level, $E$ is the evidence surface, $H$ is either a human-promotion
record or the marker that $c$ does not cross the intake-to-publication boundary,
$R$ gives one pass record, with the five fields above, for each gate in
$\bigcup_{k\in K}\Gamma(k)$, $D$ is present exactly when $K$ contains discovery
and then names the pinned discovery-gate source-interface rows used for the
claim, and $B$ records either the command-run fields or the explicit boundary
that no command-run assertion is made.  A certificate is \emph{locally
checkable} when these finite fields are present and every path, manifest row, or
log named by a field lies in the submitted artifact, the supplemental review
bundle, or the explicit path-verified historical boundary.

For later use we make the local check explicit as a finite verifier.  Given a
candidate record $\mathcal C(c)$, define $V(c,\mathcal C)$ to perform the
following schema checks, in order: (i) $K$ is a nonempty subset of the seven-kind
domain and $\ell$ is either path-verified or command-run; (ii) every element of
the finite evidence surface $E$ is a cited submitted path, review-bundle path,
manifest row, log path, pinned commit, or explicit historical-evidence boundary;
(iii) for every gate in $\bigcup_{k\in K}\Gamma(k)$, the field $R$ contains a pass
record with gate name, input surface, decision, evidence pointer, and evidence
level, and the evidence pointer is tied to $E$ or to a named manifest, table,
bundled snapshot, or historical boundary; (iv) $H$ is a concrete human-promotion record when
the claim crosses the intake-to-publication boundary and otherwise records that
no such boundary is crossed; (v) $D$ is present exactly when discovery lies in
$K$, and then names the pinned discovery-gate source-interface rows used by the
claim; and (vi) $B$ either records command, source commit, environment, exit code,
and log path for command-run evidence or explicitly records that no command-run
assertion is made.
\end{definition}

\begin{proposition}[Finite certificate schema verifier]
\label{prop:finite-certificate-schema-verifier}
For every load-bearing manuscript claim $c$ whose component kinds lie in the
seven-kind domain, $V(c,\mathcal C)$ is a finite, prose-insensitive
record-schema verifier for the declared publication certificate.  If $V$ accepts,
then $\mathcal C(c)$ is locally checkable at exactly its declared evidence level.
This is certificate-record verification only: it checks finite record shape,
dispatch, evidence pointers, and command-boundary discipline, not end-to-end
external semantic validation of the referenced artifacts or source theory.  If
$V$ rejects, then a reviewer can extract a finite bad subrecord consisting of the
first failed schema check and the fields on which that check depends.
\end{proposition}

\begin{proof}
The verifier inspects only the displayed tuple $\mathcal C(c)$, the finite
seven-kind domain, the finite dispatch table $\Gamma$, and the finite list of
paths, rows, commits, or logs cited by the record.  Since $K$ is required to be a
subset of the seven-kind domain, the set
\(\bigcup_{k\in K}\Gamma(k)\) is finite.  The checks over $E$, $R$, and the
command-run fields are therefore finite lookups in named manuscript or bundle
surfaces, not semantic judgments about generated prose.

If all six checks pass, the tuple has exactly the fields required in the
definition of a publication certificate: a finite kind set $K$, declared evidence
level $\ell$, evidence surface $E$, route-boundary field $H$, gate-record field
$R$, optional discovery field $D$ with the required presence condition, and
evidence-strength boundary $B$.  Check~(ii) is precisely the local-checkability
condition on cited paths, manifest rows, logs, pinned commits, and historical
boundaries.  Checks~(iii)--(vi) prevent the only possible escalations of the
declared level: missing gate passage, unrecorded route promotion, unsupported
discovery routing, and command-run assertion without command-run fields.  Thus an
accepted record is locally checkable at the level $\ell$ it declares, and no
stronger level is silently inferred.

If a check fails, the verifier stops at a finite test.  The bad subrecord is the
finite collection of fields read by that failed test: for example, $K$ and
$\Gamma$ for a gate-domain failure, $E$ for an evidence-surface failure, $K$,
$\Gamma$, $R$, and the cited evidence item for a gate-record failure, $H$ for a
promotion failure, $K$ and $D$ for a discovery-field failure, or $\ell$ and $B$
for an evidence-level failure.  This subrecord is independent of any surrounding
paragraph that may have described the claim.\qed
\end{proof}

\begin{theorem}[Record-acceptance exactness]
\label{thm:record-acceptance-exactness}
Fix the seven-kind dispatch table $\Gamma$, the two evidence levels, and the
certificate tuple format of Definition~\ref{def:operational-acceptance-interface}.
For a load-bearing claim $c$ and a finite candidate certificate
$\mathcal C(c)=(K,\ell,E,H,R,D,B)$, define
$\mathsf{Acc}_{\Gamma}(c,\mathcal C)$ to mean that the following six finite
record clauses hold:
\begin{enumerate}
\item $K$ is a nonempty set of declared claim kinds in the seven-kind domain and
$\ell$ is one of the two evidence levels;
\item every item of $E$ is a submitted path, review-bundle path, manifest row,
log path, pinned commit, or explicit historical-evidence boundary available to
the reviewer at level $\ell$;
\item for every gate in $\bigcup_{k\in K}\Gamma(k)$, $R$ contains a pass record
with gate name, input surface, decision, evidence pointer, and evidence level,
and the pointer lies in $E$ or in a named submitted table, manifest row, bundled
snapshot, or historical boundary;
\item $H$ records human promotion exactly when the claim crosses the
intake-to-publication boundary, and otherwise records that no such boundary is
crossed;
\item $D$ is present exactly for discovery-kind claims and then names the pinned
discovery-gate source-interface rows used by the claim; and
\item $B$ records the command, source commit, environment, exit code, and log path
for command-run evidence, or records that no command-run assertion is made.
\end{enumerate}
Then the finite verifier $V$ accepts $\mathcal C(c)$ if and only if
$\mathsf{Acc}_{\Gamma}(c,\mathcal C)$ holds.  Moreover, if $V$ accepts a record
for $c$, the same record cannot certify any stronger reading $c^{+}$ that adds a
new claim kind, a stronger evidence level, an omitted route crossing, an omitted
discovery interface, an omitted pass record, or a command-run assertion: such a
reading has a finite bad subrecord of the corresponding clause.  Thus $V$ is
exact for this paper's finite record-acceptance relation, while remaining silent
about external semantic validity of the referenced theory or artifacts and about
the soundness of any deployed gate implementation beyond the recorded pass rows.
\end{theorem}

\begin{proof}
The definition of $V$ and the six clauses above use the same finite inputs.  The
first check of $V$ is clause~1.  The second check is clause~2.  The third check is
clause~3, including both assigned-gate coverage and the requirement that each
evidence pointer be tied to the declared review surface.  The fourth, fifth, and
sixth checks are exactly clauses~4, 5, and 6.  Therefore, if
$\mathsf{Acc}_{\Gamma}(c,\mathcal C)$ holds, every verifier check succeeds and
$V$ accepts.

Conversely, suppose $V$ accepts.  Reading the successful checks in order gives
precisely clauses~1--6: the kind set and evidence level are in the permitted
domains; the evidence surface is reviewer-available at the declared level; every
gate assigned by $\Gamma$ has a pass record with the required five fields and an
allowed pointer; promotion and non-promotion are separated by $H$; discovery-kind
claims and only discovery-kind claims carry $D$; and $B$ fixes the command-run
boundary.  Hence $\mathsf{Acc}_{\Gamma}(c,\mathcal C)$ holds.

For the final assertion, keep the accepted tuple fixed and consider a proposed
stronger reading $c^{+}$.  If $c^{+}$ adds a claim kind, the finite set of gates
assigned by $\Gamma$ grows unless the added kind is vacuous in this interface;
without the corresponding pass records clause~3 fails, and if the kind lies
outside the seven-kind domain clause~1 fails.  If $c^{+}$ raises the evidence
level to command-run, clause~6 fails unless the command, commit, environment,
exit code, and log path are present.  If it adds a route crossing, clause~4 fails
unless $H$ contains the human-promotion record.  If it adds discovery content,
clause~5 fails unless the pinned discovery rows are named.  If it asserts a new
gate-dependent conclusion without a pass record, clause~3 fails.  In each case
the failed clause reads only finitely many fields, so deleting irrelevant unread
fields gives an inclusion-minimal bad subrecord.  If none of the clauses changes,
then $c^{+}$ is not stronger in the record semantics: the certificate still
licenses only the same kind set, same evidence level, same gate records, same
route boundary, same discovery interface, and same command boundary.\qed
\end{proof}

\begin{proposition}[Deterministic claim-kind dispatch]
\label{prop:claim-kind-dispatch}
For every load-bearing manuscript claim whose kind lies in the seven-kind domain
above, $\Gamma$ assigns a unique finite set of deterministic gates.  In a
pipeline that is gate-sound for acceptance, a mixed load-bearing claim may be
used as accepted work only if its acceptance entry records passage through every
gate in the union assigned to its component kinds.
\end{proposition}

\begin{proof}
The seven atomic clauses in the definition of $\Gamma$ assign one explicitly named
finite gate set to each atomic claim kind.  Hence an atomic claim has a unique
assigned gate set.  For a mixed claim, the component-kind set is finite because
it is a subset of the seven-kind domain; taking the union of the corresponding
finite gate sets is deterministic and finite.  Gate-soundness for acceptance
requires the acceptance entry of a load-bearing claim to record passage through
every gate assigned by $\Gamma$.  If a component gate of a mixed claim were
omitted, then the projection of the claim to that component kind would lack its
assigned pass record.  Such an entry would not be gate-sound.  Therefore accepted
mixed claims in a gate-sound pipeline must pass every gate in the union.\qed
\end{proof}

\begin{theorem}[Finite certificate obstruction skeleton]
\label{thm:finite-certificate-obstruction-skeleton}
Let $c$ be a load-bearing manuscript claim whose component kinds lie in the
seven-kind domain.  The verifier of
Proposition~\ref{prop:finite-certificate-schema-verifier} gives the following
complete audit classification at the declared evidence level.  A certificate for
$c$ passes the publication-safety interface if and only if it has no bad
subrecord of the following five types:
\begin{enumerate}
\item missing evidence surface for the declared evidence level;
\item missing pass record for a gate in $\bigcup_{k\in K}\Gamma(k)$;
\item missing human-promotion record when the claim crosses from intake or
source material into active publication work;
\item discovery escalation without the pinned discovery-gate source-interface
rows for certificate, ledger, lineage, and boundary witnesses; or
\item command-run escalation without command, source commit, environment, exit
code, and log path.
\end{enumerate}
Equivalently, every unsafe accepted claim contains an inclusion-minimal finite
bad subrecord of one of these five types, and deleting all other fields preserves
the same rejection by the verifier.  This is an audit-skeleton theorem for the
software-workshop route: it classifies finite certificate failures and makes no
claim about theorem-proving complexity or about fresh execution of the
underlying workflow.
\end{theorem}

\begin{proof}
Let $K$ be the finite set of component kinds of $c$.  Since $K$ is a subset of
the seven-kind domain, Proposition~\ref{prop:claim-kind-dispatch} gives a unique
finite required gate set
\[
G(c)=\bigcup_{k\in K}\Gamma(k).
\]
The certificate field $R$ is indexed by exactly this finite set, so checking
gate passage is a finite lookup: each $g\in G(c)$ must have a pass record and the
record must cite an item of the finite evidence surface $E$.  The evidence-level
field $\ell$ and boundary field $B$ make the same lookup finite for evidence
strength: at path-verified level the certificate must name the source, artifact,
pinned commit, local publication path, or gate-decision surface used by the
claim; at command-run level it must additionally name command, source commit,
environment, exit code, and log path.  Neither lookup interprets artifact
semantics, reruns Lean, or predicts editorial outcomes; those are stronger claim
kinds or stronger evidence levels that require their own records.  The human-promotion field $H$ separates
the route boundary from all other gates: it is either a concrete promotion
record or a finite marker that no such boundary is crossed.  Finally, when
discovery lies in $K$, the discovery field $D$ names the pinned source-interface
rows certified by Lemma~\ref{lem:source-interface-extraction-correctness} and
Propositions~\ref{prop:reviewable-source-snapshot-interface} and
\ref{prop:source-interface-record-file-consistency}; these rows are finite and
therefore locally checkable in the same way as the other certificate fields.
Thus the certificate is sufficient for a reviewer to check safety by examining a
finite list of fields and cited artifacts, not by trusting generated prose.

It remains to prove that the displayed obstruction list is complete.  Suppose an
accepted claim fails the publication-safety interface.  Choose an inclusion-minimal
subrecord of its acceptance entry that still witnesses failure.  If the failure
is that the claim is not tied to evidence at the declared evidence level, then
the minimal subrecord is type~1.  If evidence exists but some required gate is
unrecorded, the omitted gate belongs to $G(c)$ by the deterministic dispatch
proposition, giving type~2.  If all required non-route evidence is present but
the claim entered active publication state from intake or source material without
human promotion, the missing field is $H$, giving type~3.  If the claim is a
discovery claim and the problem is that statement-only, code-only, mechanical,
compression-only, or classifier-scored output was accepted without the pinned
certificate, ledger, lineage, and boundary interface, the missing discovery
field is $D$, giving type~4.  The only remaining way to fail while the preceding
fields are present is to assert command-run strength without the command-run
fields required by the evidence-level definition; that is type~5.  These cases
cover the definitions of acceptance entry, gate-soundness, human promotion,
discovery routing, and evidence level.  Minimality removes irrelevant fields and
leaves exactly one of the five obstruction skeletons.  Conversely, if no bad
subrecord of type~1--5 is present, then each schema check in
Proposition~\ref{prop:finite-certificate-schema-verifier} succeeds: the evidence
surface is present at the declared level, every required gate has its recorded
pass, the route-boundary field is correct, discovery rows are present exactly
when required, and command-run strength is not asserted without command-run
fields.  Hence the verifier accepts the certificate and the publication-safety
interface holds for $c$ at the declared evidence level.

The final sentence follows from the construction.  The verifier reads only the
finite certificate fields and the finite dispatch table, so the theorem
classifies certificate failures for review.  It does not assert a lower bound,
complexity separation, automated theorem-proving method, or fresh run of any
external command.\qed
\end{proof}

\begin{proposition}[Gate-interface separation]
\label{prop:gate-interface-separation}
The promotion, overlap, submission-state, and theorem-content delta gates are
separate deterministic interfaces.  None can be replaced by passage of another
one when a load-bearing claim has the corresponding component.
\end{proposition}

\begin{proof}
Each named gate has a distinct invariant and evidence surface in the operational
definition.  Promotion asks whether a candidate has crossed the human
publication boundary; its evidence is the active-paper directory and pipeline
metadata.  Overlap asks whether the route duplicates or conflicts with a sibling
route; its evidence is route identity, overlap ledgers, submitted-sibling paths,
and board state.  Submission-state asks whether the proposed publication action
is compatible with submission markers, venue state, and submission-pack metadata.
The theorem-content delta gate asks whether an asserted extension contains
load-bearing theorem growth; its evidence is an inventory, hard-lint surface, or
delta record.  These predicates are logically independent at the interface
level: an active paper can still overlap a submitted sibling, a route with no
overlap can still have an impermissible submission state, and a compiling edit in
a permissible route can still lack theorem-content delta.  Therefore a
load-bearing claim with any one of these components must pass that component's
own gate, and passage through the others cannot supply the missing evidence.\qed
\end{proof}

\begin{proposition}[Scheduler selection is advisory before discovery gating]
\label{prop:scheduler-selection-advisory}
Let $s$ be a scheduler or critical-path score attached to a candidate claim
$c$.  If $s$ recommends selecting $c$, then the recommendation is a
work-selection claim and by itself can only pass the scheduler gate.  If $c$ is
also asserted to be a discovery or classifier-shifting contribution in a
gate-sound pipeline, then the accepted mixed claim must pass both the scheduler
gate and the discovery gate.
Consequently, critical-path scores may prioritize review order, and the imported
classifier-shift selection rule may break ties among otherwise equal discovery
potential coordinates, but neither score nor recommendation accepts a
classifier-shift discovery unless the discovery gate also supplies the required
certificate, ledger, and lineage witnesses.
\end{proposition}

\begin{proof}
By the definition of $\Gamma$, a scheduler recommendation has claim kind
work-selection, so its atomic gate is the scheduler gate.  The scheduler gate's
evidence surface records a score, backlog window, or analogous critical-path
priority; none of these fields is a semantic naming certificate, a ledger
witness, a DNA-complete theorem genome, a score certificate for a discovery
claim, a lineage witness, or a not-claimed boundary.  Hence scheduler passage
alone records only that $c$ is an eligible or prioritized work item.

Now suppose that the same recorded assertion also says that $c$ is a discovery
or classifier-shifting contribution.  Then the assertion is mixed: it has a
work-selection component and a discovery component.  Proposition~\ref{prop:claim-kind-dispatch}
therefore requires passage through every gate in the union assigned by $\Gamma$,
namely the scheduler gate for the work-selection component and the pinned
discovery gate for the discovery component.  The source-interface record in
Table~\ref{tab:source-interface-record} includes the imported classifier-change
selection theorem only in its bounded form: with positive classifier-change
weight and all other coordinates fixed, such a selection operator favors the
classifier-changing candidate.  The same source-interface record also includes
pipeline safety, which requires certificate, ledger, genome, score, lineage, and
boundary witnesses for accepted discovery.  Combining these two imported
interfaces gives the stated conclusion: scheduling and classifier-shift scoring
can advise selection order, but discovery acceptance still occurs only through
the discovery gate.\qed
\end{proof}

\begin{theorem}[Conditional publication safety interface]
\label{thm:publication-safety-interface}
Consider a theory-to-paper pipeline with the operational interface above.  Assume
that every load-bearing claim in an active manuscript is either rejected or has an
acceptance entry with an evidence surface; that the pipeline is gate-sound for
acceptance, meaning that a recorded acceptance entry is present only after every
gate assigned by $\Gamma$ to the claim kind has already produced a pass record;
that every advisory output is demoted unless the deterministic gate set
$\Gamma$ for its claim kind passes; that discovery claims are checked through
the pinned discovery-gate interface certified by
Lemma~\ref{lem:source-interface-extraction-correctness} and
Propositions~\ref{prop:reviewable-source-snapshot-interface},
\ref{prop:source-interface-record-file-consistency}, and
\ref{prop:source-interface-evidence-level-separation}, in particular the
separated manual/path-verified and executable finite-record levels for the
pipeline safety and main pipeline theorem labels; and
that no inactive intake seed is
treated as publication work without human promotion.  Then, conditional on those
workflow assumptions, any accepted load-bearing claim in the manuscript admits a
locally checkable publication certificate $\mathcal C(c)$ accepted by the finite
schema verifier of Proposition~\ref{prop:finite-certificate-schema-verifier};
equivalently, by Theorem~\ref{thm:record-acceptance-exactness}, it satisfies the
record-acceptance semantics for the dispatch table $\Gamma$.
Consequently the claim has a recorded evidence surface, a declared evidence
boundary, and a prior pass record for every gate required for its claim kind.
Moreover, accepted discovery claims inherit the bounded pinned source-interface
consequences that statement-only, code-only, mechanical-expansion, and
compression-only outputs are not accepted as discovery without the required
certificate, ledger, and lineage witnesses.  Any purported accepted claim without
such finite certificate data is rejected by one of the five obstruction skeletons
in Theorem~\ref{thm:finite-certificate-obstruction-skeleton}.  For the current
package, the hypotheses are witnessed by the machine-readable evidence map in
Proposition~\ref{prop:machine-readable-certificate-records}, the acceptance
ledger in Proposition~\ref{prop:current-package-acceptance-certificate-ledger},
and the four path-complete case witnesses of
Proposition~\ref{prop:path-complete-case-witnesses}, with the case-snapshot
non-rerun boundary isolated in
Corollary~\ref{cor:case-snapshot-non-rerun-rigidity}.  This theorem is a
conditional safety interface for that architecture: it does not independently
prove that an arbitrary implementation is gate-sound, that every possible gate in
the surrounding project was run for this package, that Lean-facing contextual
rows are current formal-source certificates, or that path-verified rows are
command-run evidence.
\end{theorem}

\begin{proof}
Let $c$ be an accepted load-bearing claim in the manuscript.  The conclusion has
three parts.  The first part constructs the certificate.  The acceptance-entry
hypothesis supplies the claim-kind set $K$, evidence level $\ell$, and evidence
surface $E$, so the decision is attached to a source path, artifact path,
command log, inventory, or witness record rather than to generated prose alone.
Gate-soundness supplies the pass-record field $R$ for every gate assigned by
$\Gamma$.  If accepting $c$ crosses from intake or source material into
daemon-visible publication work, the promotion assumption supplies the human
promotion field $H$; otherwise $H$ records that no such boundary is crossed.  The
evidence-level definition supplies the boundary field $B$: either the command-run
fields are present or the record explicitly remains path-verified.  If $c$ is a
discovery claim, the discovery-routing assumption supplies $D$ from the pinned
source-interface rows; otherwise $D$ is absent as required by the certificate
schema.  Thus $\mathcal C(c)=(K,\ell,E,H,R,D,B)$ is locally checkable whenever its
cited paths and manifest rows lie in the submitted artifact, review bundle, or
explicit historical boundary.  The same construction verifies
$\mathsf{Acc}_{\Gamma}(c,\mathcal C)$, so
Theorem~\ref{thm:record-acceptance-exactness} identifies the constructed
certificate with the paper's independently stated record-acceptance semantics,
not merely with an informal unpacking of the tuple.

Propositions~\ref{prop:claim-kind-dispatch} and
\ref{prop:gate-interface-separation} identify the required finite gate set:
formal-source claims use build and axiom gates, traceability claims use inventory
and marker gates, route claims use promotion, overlap, and submission-state
gates, artifact claims use status and limitation-ledger gates, submission claims
use submission-pack gates, extension-style discovery claims use the
theorem-content delta gate together with the pinned discovery gate,
work-selection claims use the scheduler gate, and mixed claims use the union.

advisory-output assumption prevents an agent draft, review packet, score, or
repair proposal from being promoted by prose alone: without the relevant pass

inactive intake seed from becoming publication work merely because a local source
path exists.

If $c$ is a discovery claim, the discovery-routing assumption sends it through

record-file consistency certificate in

source-interface table records the imported statements used here:
statement-only, code-only, mechanical-expansion, and compression-only records do

\begin{lemma}[Gate-witness criterion]
\label{lem:gate-witness-criterion}
A case record is a path-verified witness for the safety interface when it names
the source or artifact surface, the invariant that failed, the gate decision,
and the safe manuscript lesson.  Under Theorem~\ref{thm:publication-safety-interface},
such a witness can support a case-study claim, but not a stronger command-run
claim, unless the corresponding command log is also recorded.
\end{lemma}

\begin{proof}
The four named fields are exactly the data required by the definition of a
path-verified evidence level: they identify where the case is checked, which
gate predicate is being evaluated, what decision was made, and which bounded
claim may be carried into the manuscript.  The definition of command-run
evidence has additional required fields: command, source commit, environment,
exit code, and log path.  Therefore a witness record with only the four
path-verified fields supports the bounded case-study claim and cannot be used
as evidence for a fresh command-run assertion.\qed
\end{proof}

\begin{proposition}[Path-complete case witnesses]
\label{prop:path-complete-case-witnesses}
Suppose a case-study row is used as load-bearing evidence for
Theorem~\ref{thm:publication-safety-interface}.  If the row is path-complete in
the sense above, then the row supplies exactly the evidence surface required for
a path-verified historical case claim and no evidence surface for a fresh daemon,
full-source, theorem-content, artifact-suite, or semantic-substrate rerun.  In
particular, a promotion row is sufficient only
for the bounded claim that an intake packet is not daemon-visible publication
work before human promotion; a route-overlap row is sufficient only for the
bounded claim that the overlap and submission-state gates blocked advancement
until one of the recorded next actions occurs; a theorem-content row is
sufficient only for the bounded claim that file churn or compilation did not
show substantive theorem growth; and an artifact-limitation row is sufficient
only for the bounded claim that the artifact limitation must be disclosed or must
block promotion.
\end{proposition}

\begin{proof}
Let $r$ be a path-complete case row.  By definition, every load-bearing
component of $r$ has a concrete source or artifact path.  The promotion
interface names the candidate surface, human-promotion evidence, active-paper
markers, gate decision, and the bounded manuscript claim; these fields are
precisely the data needed to distinguish inactive intake from publication work.
The route-overlap interface names the active route, the submitted sibling that
creates the chronology constraint, the reason for overlap, the gate decision,
and the finite set of permitted next actions.  These are precisely the data
needed to check whether advancement is allowed without appealing to generated
prose, and the submission-state evidence prevents a route from racing an already
submitted sibling.  The theorem-content interface names the changed surface,
the theorem inventory or hard-lint surface, the substantive-content delta, the
gate decision, and the allowed manuscript claim; these fields are precisely the
data needed to reject extension claims based only on file churn or successful
compilation.  The artifact-limitation interface names the status file, the
limitation ledger, the observed limitation, the gate decision, and the only
manuscript claim that may be carried forward.  These are precisely the data
needed to prevent a failed or bounded artifact check from being promoted into a
stronger dynamic-validation claim.  Lemma~\ref{lem:gate-witness-criterion} then
applies to each such row:
the named paths give the source surface, the interface fields give the failed
invariant and decision, and the last field gives the safe lesson.  The same
lemma also rules out upgrading the row to a command-run claim unless the extra
command-run fields are recorded.  In particular, the proof does not rerun the
publication daemon, overlap scanner, theorem-content detector, artifact suite,
or GroundCompiler evaluator; it proves only that the historical path surfaces are
sufficient for the bounded lessons displayed in the table.\qed
\end{proof}

\begin{theorem}[Evidence-level overclaim obstruction]
\label{thm:evidence-level-overclaim-obstruction}
Fix the certificate schema, dispatch function, and evidence-level vocabulary of
this paper.  Let $c$ be a load-bearing claim whose accepted certificate has
level path-verified and whose boundary field $B$ records that no command-run
assertion is made.  Then every stronger reading of $c$ that asserts any of the
following additional conclusions is rejected by the finite schema verifier:
\begin{enumerate}
\item external gate soundness for an arbitrary implementation of the workflow;
\item Lean correctness, full-source rebuild success, or axiom-purity beyond the
recorded formal-source gate fields;
\item end-to-end external semantic validity of artifact data beyond the finite
manifest and evaluator surfaces named in $E$ and $R$;
\item a fresh daemon run, full-source rerun, Rule110 or GroundCompiler rerun, or
journal or workshop acceptance; or
\item bundle-backed reviewability when neither \path{review_bundle/} nor an
archival equivalent carrying the same finite records is in the submitted
artifact boundary.
\end{enumerate}
More precisely, such a stronger reading has an inclusion-minimal bad subrecord of
one of the five types in
Theorem~\ref{thm:finite-certificate-obstruction-skeleton}.  Hence the accepted
claim is rigid at its declared evidence level: path-verified certificate records
cannot be promoted by prose into command-run evidence, semantic validation,
formal-source correctness, or external acceptance.
\end{theorem}

\begin{proof}
Let $c^+$ be one of the stronger readings.  It has the same displayed manuscript
sentence as $c$ but a larger claim-kind set, a stronger evidence level, or a
larger submitted-artifact boundary requirement.  The verifier does not inspect
rhetorical emphasis; by Proposition~\ref{prop:finite-certificate-schema-verifier}
it inspects only the finite tuple
$\mathcal C=(K,\ell,E,H,R,D,B)$ and the finite dispatch table.

If $c^+$ asserts external gate soundness for an arbitrary implementation, then
it is not merely the conditional theorem-interface claim accepted by
Theorem~\ref{thm:publication-safety-interface}.  It needs pass records showing
that the relevant implementation ran every gate in
$\bigcup_{k\in K}\Gamma(k)$.  Those records are not supplied by the
path-verified certificate for $c$, so the minimal bad subrecord is a missing
pass-record obstruction of type~2.  If $c^+$ asserts Lean correctness,
full-source rebuild success, or axiom-purity, then it is a formal-source or
command-run claim.  Proposition~\ref{prop:formal-source-gate-instantiation}
identifies the required build, axiom-purity, and command-run fields; when they
are absent, the minimal bad subrecord is type~2 for missing formal-source gates
or type~5 for command-run escalation.

If $c^+$ asserts end-to-end semantic validity of artifacts beyond the named
manifest and evaluator surfaces, then it has an artifact component not covered
by the finite status and limitation-ledger records in $R$.  The current
acceptance and certificate ledgers display only the bounded artifact row $a_6$:
its evidence surface is the Rule110 status file, limitation ledgers,
paper-data reference, and review-bundle manifest, and its boundary field says
that no fresh artifact rerun is asserted.  A stronger artifact claim therefore
lacks an assigned artifact pass record, giving type~2,
or asserts a fresh evaluator run without command-run fields, giving type~5.  The
same argument covers a fresh daemon run, full-source rerun, and Rule110 or
GroundCompiler rerun: each is a command-run or artifact-strength escalation and
is rejected by the missing gate or command-run boundary fields.

If $c^+$ asserts journal or workshop acceptance, then its acceptance-entry field
would have to contain an editorial or venue acceptance record.  The operational
notion of acceptance entry in this paper is internal and submission-local; the
current ledger contains no external editorial acceptance row.  Thus the stronger
reading either lacks the required route/submission pass record, giving type~2,
or lacks the relevant external evidence surface, giving type~1.  Finally, if a
bundle-backed claim is made while no review bundle or archival equivalent lies
inside the submitted artifact boundary, the evidence item named by the
certificate is absent from $E$ at the declared level, so the minimal bad
subrecord is type~1.  These cases exhaust the displayed stronger readings.
Theorem~\ref{thm:finite-certificate-obstruction-skeleton} then gives the stated
classification and proves rigidity at the declared evidence level.\qed
\end{proof}

\begin{proposition}[Review-bundle archive-equivalence criterion]
\label{prop:review-bundle-archive-equivalence}

Table~\ref{tab:review-bundle-archive-equivalence}.  Equivalently, it must have

certificate file list, the same SHA-256 content digests at final packaging time,

\end{proposition}

\begin{proof}
The manifest identity criterion fixes the root record that all bundle-dependent
claims cite: \path{review_bundle/REVIEW_BUNDLE_MANIFEST.json}.  Allowing only an
additional archive locator field prevents the archive from silently changing the
certificate schema, pass-record ledger, submission-interface map,
primary-claim inventory, verifier scripts, verifier logs, pinned-source
snapshot, case-evidence rows, or submission-artifact declaration.  The bundle
version is finite because the current manifest carries the three displayed
fields \path{bundle_kind}, \path{created}, and
\path{public_interface.public_source_commit}; equality of the tuple rules out
substituting a different support bundle or a different pinned source commit.

The finite file-list criterion is obtained by following only the manifest and
the machine-readable interface records already used in the proofs: certificate
schema, current pass records, primary-claim inventory, submission-interface map,
verifier scripts and logs, source snapshot, and the case snapshots named in the
case-evidence rows.  This traversal is finite because each record is a finite
JSON or manuscript table row and because generated interpreter caches are not
certificate surfaces.  The content-hash criterion then gives a byte-level test
for every file on that finite list.  If a file is omitted, added as a replacement
for a named certificate surface, or changed bytewise, either the file-list row or
the SHA-256 row fails.  The path-semantics row prevents a hash-correct file from
being moved under a new relative name that would make manuscript paths point to a
different object.

When all five rows pass, every path used by a bundle-dependent theorem,
proposition, table row, verifier record, or manifest row denotes the same bytes
under the same relative name and under the same root manifest identity as in the
submitted \path{review_bundle/}.  Thus the archive is equivalent for exactly the
finite certificate checks made in this paper.  When any row fails, a reviewer has
a finite bad subrecord: the changed manifest identity, changed version tuple,
file-list discrepancy, hash mismatch, or path-retargeting witness.  In that case
the archive is not accepted, and the support surface must be the exact uploaded
\path{review_bundle/} directory.\qed
\end{proof}
