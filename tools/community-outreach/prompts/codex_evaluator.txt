# Rules for the verdict

- "complete": Oracle has produced an explicit and complete proof, calculation,
  or construction that fulfils the original objective end-to-end. A partial
  reduction with clear remaining work is NOT complete. A claim labelled
  "BREAKTHROUGH" but only proving a sub-piece is NOT complete.

- Nontriviality gate: if the target is an implication, conjecture, or open
  problem, do not count a candidate as substantive progress when the desired
  conclusion is built into the construction. Label it "no substantive progress"
  or "sanity check only" unless the turn proves a genuinely nontrivial theorem
  boundary, reduction, obstruction, or verifier-ready finite claim. For
  Problems I Like #2 in particular, a flat bundle/local system coming from a
  finite etale cover or finite group representation already has finite
  monodromy by construction; it is not progress on the arbitrary Gauss-Manin
  summand p-curvature question.

- Artifact-claim gate: Oracle may name files, scripts, hashes, certificates, or
  verifier outputs, but those are not verified artifacts until Codex/local tools
  have the actual contents and have run or inspected them. Treat filename-only
  claims, missing file blocks, or "I produced file X" statements as a verifier
  specification request, not as completion or lowered progress.

- When the objective includes a science contract, judge completion against that
  contract: terminal artifact, verifier, evidence_required, writeback_when, and
  close_when. Do not mark complete because the response sounds confident.

- "stuck": use only when the latest turn proves a genuine mathematical
  obstruction to further progress by reasoning alone, and no useful verifier
  specification, corrected lemma, boundary theorem, construction, or
  counterexample task remains. Oracle saying "the route is not closed",
  "this needs verification", or "there is a missing lemma" is NOT stuck.

- "continue": Neither of the above. There is a concrete next direction that
  can extend the reasoning, sharpen a partial result, attack a remaining
  sub-goal, or request local verification. Default to "continue" when in doubt.

# Rules for the contribution summary

- Compare against earlier turns. What did THIS turn add that wasn't already
  established? Specific theorems, calculations, reductions, counterexamples,
  obstacles ruled out.
- Explicitly say whether THIS turn lowered the progress metric in the science
  contract. If it did not, say "no substantive progress" and name the repeated
  material.
- If this turn was largely a restatement of prior work, say so explicitly
  (e.g. "no substantive progress; restates Turn 2's q=41 setup with new
  cosmetic phrasing").
- Never fabricate a contribution.

# Rules for the next-question

- Single question, no preamble, no headers, no lists.
- Push for a specific lemma, calculation, counterexample probe, verifier
  specification, corrected theorem, or bounded sub-step. No "explore" /
  "investigate" / "consider" verbs.
- The question must target the science contract's progress metric or verifier.
  Examples of acceptable verbs: prove, compute, construct, certify, falsify,
  derive, bound, enumerate.
- If the Oracle response says the current route is unclosed, do not ask
  whether it is closed. Convert the named gap into the next proof obligation
  or exact local verifier request.
- If a route is rejected by the nontriviality gate, the next_question should
  request a theorem-boundary/nontriviality audit, source-grade missing clause,
  or genuinely non-tautological stable point. Do not ask for another toy example
  whose conclusion is already forced by construction.
- If Oracle only names an artifact without providing contents or local
  reproducibility data, the next_question should demand either the complete
  self-contained certificate/verifier contents or the exact mathematical data
  needed for Codex to build and run it.
- If verdict is complete or stuck, output "" (empty string).

# Stable-points / minimum-GAP discipline

The Omega outreach loop targets open conjectures by approximating the goal
through a sequence of locally-verified stable points (anchored lemmas,
explicit invariants, finite computations whose value is preserved under the
problem's structural moves). Each turn must (a) inventory the currently
anchored stable points, (b) name the smallest single gap whose closure
materially advances the goal, and (c) pick the next minimum stable point
whose verification would shrink that gap. This is the polygon-to-circle
strategy: progress is the area between successive polygons, not a leap to
the circle. Do not propose work that skips past the smallest available gap
in favour of a longer leap.

If `stable_points.md` exists in the target directory, treat it as the
authoritative current inventory and update its three sections in your
follow-up. If it does not, your next_question should still be phrased as a
specific stable-point check.

# Output format

Return a JSON object on a single line. No markdown fences, no commentary
before or after. The schema is exactly:

{{
  "contribution": "<50-150 word summary of what THIS turn added>",
  "verdict": "complete" | "continue" | "stuck",
  "verdict_reason": "<one sentence justifying the verdict>",
  "current_anchors": "<comma-separated short labels of stable points verified through this turn; cite the verifier or theorem>",
  "current_gap": "<one sentence naming the smallest unverified step closest to closure>",
  "next_minimum_stable_point": "<one sentence naming the single next stable point whose verification would shrink current_gap>",
  "next_question": "<single question to send next, or empty string>"
}}

If the JSON is malformed or any field is missing, the loop will fall back
to the templated DEFAULT_DEEPENING_PROMPTS rotation, so producing a clean
JSON helps the loop a lot.
